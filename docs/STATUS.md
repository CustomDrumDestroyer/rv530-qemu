# Status

Per-module state of the RV530 (Radeon X1600) device model.

In one sentence: Mac OS X 10.6.8 runs on the emulated X1600 with Apple's
unmodified ATI drivers, with Quartz Extreme and Core Image on the emulated
GPU and fragment work on the host GPU through Vulkan; Linux's `radeon`
driver is the reference path.  Hosts: x86_64 Linux with KVM (the
reference), Apple silicon macOS under multi-threaded TCG, and Intel macOS
under Hypervisor.framework, with the Vulkan backend on MoltenVK on macOS
(the top-level README's "macOS hosts" section).

## Device model (`qemu/hw/display/rv530/`)

| File | State |
| --- | --- |
| `rv530.c` | PCI device (1002:71C5, subsystem 106B:0080), BAR0 256 MiB VRAM aperture, BAR2 64 KiB MMIO, BAR4 I/O alias, expansion ROM.  Register file, MM_INDEX/DATA and the PLL/PCIE/MC indirect spaces, interrupts (INTx and MSI), the polling-loop detector, BQL stall reports (`RV530_STALL_MS`), QOM properties including the run-time `auto-resize` and `resize-to`.  MMIO opts out of QEMU's re-entrancy guard and keeps its own, so other vCPUs wait instead of losing accesses while a CP run has released the BQL. |
| `r5xx_mc.c` | MC address space (FB/AGP locations), RV370-style PCIe GART with a page cache, GPU address translation for every engine. |
| `r5xx_cp.c` | Ring and indirect buffers, PM4 types 0/2/3, RPTR and scratch write-back, software interrupt.  Runs synchronously in the vCPU that writes `CP_RB_WPTR` (`cp-sync`) and releases the BQL while it only waits (shader compiles, CPU raster workers, long GPU batch waits). |
| `r5xx_avivo.c` | D1/D2 scanout (linear and tiled, 8-64 bpp), CRTC timing with vblank and scanline counters at the programmed rate, hardware cursor with hot-spot recovery, DC LUT gamma on every format, HPD, and the DDC buses.  Window-driven resolution changes. |
| `r5xx_edid.c` | Own EDID 1.3 + CEA-861: CVT reduced-blanking timings up to 2560x1600, the preferred size at `refresh` Hz, capped at the 330 MHz dual-link pixel clock Apple's driver accepts (2560x1440 gets 81 Hz). |
| `r5xx_atom.c` | Mailbox behind the synthetic AtomBIOS (`scripts/atombios/mkrom.py`). |
| `r5xx_2d.c` | Legacy 2D engine: fills, blits, host data, byte-swapped system-memory sources. |
| `r5xx_3d.c` | 3D engine glue: state latching, PVS/US uploads, draw packets, vertex fetch, clipping, MSAA resolve; sends each draw to the Vulkan backend or the CPU path. |
| `r5xx_pvs.[ch]` | Vertex program decoder, interpreter (Apple's fixed-function lighting programs included), disassembler, GLSL emitter. |
| `r500_us.[ch]` | Fragment program decoder, quad interpreter, disassembler, GLSL emitter for the Vulkan backend. |
| `r5xx_tex.[ch]` | Texture decoding and layout (mips, cube, 3D, tiling), every R300/R500 format including DXT, ATI1N/2N, and Y'CbCr 4:2:2, sampling, render-target pack/unpack. |
| `r5xx_raster.[ch]` | CPU rasterizer: triangles, lines, points, depth/stencil, alpha test, blending, logic ops.  Large draws run on a worker pool. |
| `r5xx_vk.[ch]`, `r5xx_vk_state.c`, `r5xx_vk_frag.glsl` | Vulkan backend: rasterization, fragment programs, texturing (2D, rectangle, 3D, Y'CbCr), blending, and depth/stencil on the host GPU, with a device-local VRAM mirror and a persistent shader cache.  Runs on MoltenVK too: float64 is optional (exact float depth math without it), and on macOS the Metal devices are checked before MoltenVK is loaded (`r5xx_vk_mac.m`).  Draws it cannot take fall back to the CPU path; `rv530_vk_fallback` names the reason. |
| `r5xx_clip.c` | Clipboard peer for the guest agent (`snowleopard/agent`). |
| `r5xx_regnames.c` | Register names for traces (generated by `qemu/hw/display/rv530/scripts/gen_regnames.py`). |

## Known gaps

- The command processor runs synchronously in the vCPU that writes the ring
  pointer, because the guest drivers must see it busy.  A long batch keeps
  that vCPU out of the guest until the host GPU has finished it; with
  several vCPUs, a guest that waits too long for a TLB shootdown can panic
  (Mac OS X: about 250 ms).  `RV530_STALL_MS` reports long runs.
- The Vulkan backend emulates the R5xx framebuffer in a storage buffer with
  fragment-shader interlock, which serializes overlapping draws; batches of
  a few hundred draws take the host GPU 10-25 ms.
- Vertex programs and command processing are still interpreted on the CPU.
- First use of a fragment program compiles a Vulkan pipeline; the device
  keeps a persistent, prewarmed shader cache (`RV530_VK_CACHE_DIR`).
- No migration or snapshot support (the device is not migratable).
